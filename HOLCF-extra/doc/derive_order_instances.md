# Deriving order-class instances for domain-package types

Status: the Eisbach layer (`Domain_Order_Derive.thy`) is implemented. The ML command
described here is **future work**.

## What exists

`Domain_Order.thy` states each order class property for the image of a deflation, as a
locale over HOLCF `deflation`:

| locale                  | at `ID` this is          | notes                                   |
|-------------------------|--------------------------|-----------------------------------------|
| `bounded_complete_defl` | `bounded_complete`       | antitone among deflations               |
| `separated_defl`        | `separated_po`           | image-only; antitone                    |
| `separating_defl`       | `separated_po`           | one-sided (second element arbitrary); antitone; free on flat types |
| `downclosed_defl`       | (stable subdomain)       | not antitone; admissibility uses algebraicity |
| `distributive_defl`     | `distributive_cpo`       | bc + downclosed + relational law        |

Each has rules for `⊥`, `ID`, `u_map`, `ssum_map`, `sprod_map`, the `abs`/`rep` isomorphism,
admissibility, and a class intro from the predicate at `ID`. The only non-structural rule is
`distributive_defl_sprod_map`, which needs `separating_defl` of both components.

A map rule `P v ⟹ P (T_map⋅v)` is proved by fixed-point induction on the package's map
functional (`T_map ≡ Λ v. μ f. abs oo F v f oo rep`). The instance follows from the map rule at
`v = ID` and `T_map_ID`. The per-type inputs are all generated by the package:
`T_map_def`, `T.iso_rews`, `T_map_ID`. No constructor-level lemmas are needed.

`Domain_Order_Derive.thy` packages this as Eisbach methods (prefix `domain_category_`: the classes are categories of domains closed
under the domain constructions) over named-theorem registries
(`domain_category_adm`, `domain_category_bottom`, `domain_category_iso`, `domain_category_map`, `domain_category_ID`, `domain_category_deflation`,
`domain_category_below`, `domain_category_class`). Each step of a method is a single rule application, mostly out of
a registry, and every leaf goal is closed under `solves`, so a step can only succeed by doing
what it is meant to:

```isabelle
lemma separating_defl_T_map [domain_category_map]:
  "deflation v ⟹ deflation w ⟹ separating_defl (T_map⋅v⋅w)"
  by (domain_category_map_rule map_def: T_map_def iso_rews: T.iso_rews)

lemma distributive_defl_T_map [domain_category_map]:          (* recursion through ⊗ *)
  "distributive_defl v ⟹ distributive_defl w ⟹ distributive_defl (T_map⋅v⋅w)"
  by (domain_category_map_rule map_def: T_map_def iso_rews: T.iso_rews
      fix_facts: separating_defl_T_map)

instance T :: ("{domain, distributive_cpo}", "{domain, distributive_cpo}") distributive_cpo
  by (domain_category_instance map_ID: T_map_ID)
```

How `domain_category_map_rule` works:
- `T_map_def` (`T_map ≡ Λ v₁ … vₙ. μ f. G f`) is inserted as an equation and beta-reduced one
  parameter at a time by `drule map_beta_step` (`M = (Λ v. B v) ⟹ cont B ⟹ M⋅v = B v`), each
  continuity side goal closed by `solves ‹intro cont2cont›`. Any arity works, including zero
  (the package defines `T_map` for parameterless types too).
- `erule map_fix_induct` matches the reduced equation `m = μ f. G f` (premise 1) and the
  conclusion `P m` at once; this also fixes the parameters, left schematic by the `drule`s.
  `P` comes from higher-order unification; the first unifier abstracts all occurrences of `m`,
  and a wrong one (e.g. constant `P`) cannot pass `solves ‹rule domain_category_adm›`. The remaining
  premises are ordered easiest first: `adm P`, `P ⊥`, `cont G`, then the step
  `f ⊑ m ⟹ P f ⟹ P (G f)`, stated for the folded `m` (`T_map⋅v⋅w`).
- The iso rules are stated with the `abs_iso`/`rep_iso` equations of `T.iso_rews` as premises
  (interpreting `iso` locally in their proofs), and the antitonicity rules with `d ⊑ e` first,
  so all registries list source theorems as they are, without `OF` or `rotated`.
- `intro domain_category_map domain_category_ID` decomposes the rep type. Side goals are closed by the hypothesis or
  `erule domain_category_deflation`. Another predicate `Q` on the iterate `f` (separation, when recursion
  passes through `⊗`) is transferred from the fixed point: `erule domain_category_below` matches the goal
  `Q f` and the step's `f ⊑ T_map⋅v⋅w` at once, leaving `Q (T_map⋅v⋅w)`, which must be among
  `fix_facts`: the type's own map rule for `Q`, derived first. The list is explicit and short
  on purpose; only facts about the same type are ever needed there.
- `declares cont2cont`: callers can add continuity rules.
- `domain_category_instance` rewrites `ID` to `T_map⋅ID⋅…`, finds the map rule in `domain_category_map`, and closes
  the parameter premises from `domain_category_ID`.

The examples session `HOLCF-extra-Examples` (`HOLCF-extra/Examples`) exercises this on strict
and lazy lists, a two-parameter tree, a parameterless type, and nested recursion through
`slist`.

What the user still decides by hand: the parameter sorts of each instance, and the order of
derivations (side predicates such as separation before distributivity).

## The ML command (future)

```isabelle
derive_order_instances T
```

for one type or a mutually recursive group. It would:

1. **Read package data.** From the domain package's theory data, get the type constructor(s),
   `T_map_def`, `iso_rews`, `T_map_ID`, and the rep-type shape (the functional `F`). No
   name-mangling: the facts are all recorded per type.
2. **Enumerate map-rule variants.** Walk `F` and collect, per combinator position, the
   applicable rules from the registry: general rules (premises on the component maps) and
   special ones (flat components via `separating_defl_flat`; registered map rules of nested
   types). Premises at closed concrete types are discharged first-fit, or the variant is
   dropped. Premises at types that mention parameters remain as requirements on the
   parameter maps.
3. **Stratify predicates.** Order the predicates so that each one's side conditions are
   derived first: separation and separating before distributivity. A side predicate at the
   recursive occurrence is either carried through the induction or, if antitone, proved for
   the fixed point first and transferred to the iterates (as `map_fix_induct`'s
   `f ⊑ m` premise and `fix_facts` do now). Within one
   predicate the greatest fixed point is correct: assume the predicate at the recursive
   occurrence (the induction hypothesis) and propagate.
4. **Instantiate at `ID`.** Each map-rule variant at `v = ID` plus `T_map_ID` gives a
   class-level rule, `P ID('a) ⟹ … ⟹ P ID(T)`, i.e. a candidate arity.
5. **Choose the arity.** Emit the unique minimal candidate (least parameter sorts, by sort
   entailment). If there is none, fall back to the all-general variant and warn. Local
   antichain pruning is sound because requirements combine by monotone union. Flatness is a
   sort constraint (`'a::flat`), decided by `Sign.of_sort` / `Sorts.mg_domain`, not a predicate.
6. **Prove and register.** Prove the map rules by instantiating the stored rules directly
   (no search at proof time), declare them `[domain_category_map]`, and emit the instances. In ML the
   induction can be instantiated explicitly: build the closed equation
   `T_map⋅v₁⋅…⋅vₙ = μ f. G f` from the known parameters and take `P` by `abstract_over` the
   map term, as `induct` does, instead of relying on the unifier's first solution.

Mutual recursion: the functional is on a tuple of maps; fixed-point induction runs on the
tuple, with the predicate conjoined componentwise. The registry rules are unchanged.

### Open questions

- **Function spaces and powerdomains.** There are no rules yet for `cfun_map`,
  `upper_map`/`lower_map`/`convex_map`. Downward closure fails through the argument position
  of `→` and through the upper and convex powerdomains, so distributivity cannot be derived
  through them as things stand.
- **Strict parameter positions.** The arity choice per `⊗` position (both sides type
  parameters → both `{separated, distrib}`; one side flat → the other needs only
  `distrib`; …) should fall out of step 5 automatically. This needs checking against the
  hand-derived table in the project notes.
- **Prior art to mirror:** the domain package's own `domain_deflation` / `domain_map_ID` /
  `domain_isodefl` (`Tools/Domain/domain_take_proofs.ML`), AFP *Deriving* (a thin manager plus
  per-class generators with per-type-constructor info records), and Transfer/Lifting relator
  properties.
